# Spine Pair Review — CheckInn Smart Search

## Overall verdict
The delta pair is a strong contract: every UJ has a full Key Flow, every token reference resolves against the root `DESIGN.md`, and nearly every state a builder will meet is committed. Two things block a clean source-extract. The four key-screen mocks are not linked from either spine yet, and the spines contradict each other on whether the Home hero has a gradient. The rest are naming and section-shape fixes plus two under-specified states (re-running results under a Query, and what a fallback URL holds).

## 1. Flow coverage — strong
Checked PRD UJ-1, UJ-2 and UJ-3 against EXPERIENCE.md Key Flows 1–3: titles verbatim, named protagonists, numbered steps, a bold climax beat, and edge and failure paths. FR-1 to FR-20 guest-facing consequences each land in a flow, a state or a component row (FR-7 to FR-9, FR-12, FR-13 and FR-17 to FR-19 have no guest UI, which is correct).
### Findings
- **low** Flow 2 has an edge case (presenter view) but no failure path. Sipho is the natural place to show a Match reason failing or timing out on one card while the others fill (EXPERIENCE.md Key Flows, Flow 2). *Fix:* add one "Failure: a reason times out" line: Goldleaf's label and skeleton disappear, the other cards are unaffected, and "Match reasons added" still fires once.

## 2. Token completeness — strong
Extracted the 21 component entries in the DESIGN.md frontmatter and every `{path}` reference in both spines. All resolve against the root `DESIGN.md`: colors `surface`, `on-surface`, `on-surface-muted`, `primary`, `primary-subtle`, `secondary`, `tertiary`, `outline`; typography `body-md`, `body-sm`, `input-mobile`, `label-md`, `label-sm`; rounded `sm`, `md`, `full`; spacing `xs`, `sm`, `md`, `lg`. The root components named in the prose (`icon-button`, `focus-ring`, `chip`, `notice`, `divider`, `skeleton`, `icon`) all exist. No new colours, so no hex is missing. The gradient is handled as two stop components plus a prose rule, with the reason stated.
### Findings
- **low** The Cyan stop's contrast is given only as "well above it". Brand Blue gets a number (4.43:1) (DESIGN.md Colors, "Contrast of the border"). *Fix:* state it. `#00D2D6` on Midnight `#070C14` is about 10.4:1.
- **low** The forced-colours fallback says "a solid 2px system border" but names no system colour (DESIGN.md Colors, "Forced colours"). *Fix:* name it, e.g. `CanvasText` (or `ButtonBorder`), so the CSS is not a guess.

## 3. Component coverage — adequate
Component names found across both spines: Smart search box, Smart search submit, Smart search clear, Character counter, spinner / Submitting status, Search bar (changed), Criteria chip, Notice(s), Listing card (changed), Match reason, Best-fit room line, Best fit chip, Room table (changed), Score breakdown, and the weak-match heading. Most have a visual row in DESIGN.md Components and a behavioural row in EXPERIENCE.md Component Patterns, with real rules.
### Findings
- **medium** The weak-match heading and its "Try describing it another way." line are load-bearing (UJ-3, FR-10, mock `key-results-weak.html`) but have no component row in either spine. Nothing specifies the rephrase line's type role or spacing, whether it is part of the heading's accessible description (focus lands on the heading, so a screen reader may never reach the line), or how notices are attached when a weak match also has an unknown-place notice (DESIGN.md Components, Notices: "the Search results heading itself says it, in the root heading style"; EXPERIENCE.md Smart search states, Weak match). *Fix:* add a "Weak-match heading" row to both spines covering the type role of the line, `{spacing.*}`, `aria-describedby` covering the rephrase line and any notices, and the 60-character truncation (including whether the accessible name is truncated too).
- **medium** Component names drift between the spines. "Best-fit room line" (DESIGN.md) has no EXPERIENCE.md row; its rules sit inside "Listing card (changed)". "Notices" (DESIGN.md) is "Notice (Smart search)" in EXPERIENCE.md. "Listing card (changed)" and "Room table (changed)" have behaviour rows but no DESIGN.md Components entry; the card additions sit in DESIGN.md Layout & Spacing instead (DESIGN.md Components; EXPERIENCE.md Component Patterns). *Fix:* use one name per component in both files. Either give Best-fit room line its own EXPERIENCE row or rename the DESIGN entry "Listing card (changed)", and add a short "Room table (changed)" entry to DESIGN.md pointing to the Best fit chip.
- **low** The Criteria chip row is "a list labelled 'Your filters'" (EXPERIENCE.md Accessibility Floor), but neither spine says whether that label is visible. If it is, it needs a type token and a place in the layout. *Fix:* state "visually hidden label" or give it a token and position in DESIGN.md Layout & Spacing.
- **low** The spinner and the "Reading your search…" status have visual specs (DESIGN.md Components, Submitting) but behaviour only in the state table. Acceptable, but the submit's state while submitting is undefined: is it `aria-disabled`, and is a second Enter ignored? *Fix:* add one sentence to the Smart search submit row.

## 4. State coverage — adequate
Walked Home, Search results, Listing card, Hotel page room table and the Smart search box. Covered: Provider not configured, idle, typing, submitting, results, results with notices, weak match, no Preferences, no results, fallback, reason loading / arrived / failed, invalid Search bar input, Best-fit room no longer available. Offline is covered by fallback, and focus is defined after submit, chip removal and clear. Two transitions are under-specified.
### Findings
- **medium** There is no loading state for a re-run under an existing Query: removing a Criteria chip, a Search bar Search while a Query is in the URL, or Back to an earlier Smart search URL. Do the three skeleton cards from the MVP show? Do Match reasons re-stream behind skeletons, or come from a cache? FR-13 caches Relevance, not reasons. Focus stays on the next chip during the chip case, but what does the listing show meanwhile? (EXPERIENCE.md Component Patterns, Criteria chip and Search bar (changed); Smart search states). *Fix:* add a "Re-running" row: the listing becomes skeleton cards, the box and chips stay usable, reasons re-enter the Reason loading state, and focus follows the triggering control's rule.
- **medium** The fallback state does not say what URL CheckInn navigates to when interpretation fails. Interpretation produced no Hard criteria or Preferences, so the state says results "apply the Hard criteria already in the Search bar". That leaves three gaps. Does the URL carry the Query text and a fallback marker (needed for "Reloading a fallback URL does not retry the Provider")? What does a Search bar Search do on that URL, given a Query is present but has no Preferences? And on a reload of a normal Smart URL whose Preferences embedding is no longer cached and the Provider then fails, does the same notice show? (EXPERIENCE.md Smart search states, Fallback; Component Patterns, Search bar (changed)). *Fix:* add two sentences on what the fallback URL holds and how the Search bar behaves on it, and state that a reload or Back that hits a Provider failure shows the same fallback notice.
- **low** Pasting more than 300 characters is not covered. Input "stops at 300", but is the paste silently cut, and is the limit announcement triggered? (EXPERIENCE.md Component Patterns, Character counter). *Fix:* say that a paste is truncated to 300 and the same limit announcement plays.

There is no `mockups/`, `wireframes/` or `imports/` folder yet. Neither spine links any mock, and neither states "spines win on conflict". The mocks are still in `.working/`, so this is expected at this step, but it must be fixed when they are promoted.

The spines win on conflict with any mock." State the spines-win rule once, here.
  - **EXPERIENCE.md Smart search states**: link Submitting → `key-home-smart.html` (Submitting alternates); Results and Reason loading → `key-results-thandi.html`; Weak match and Results with notices → `key-results-weak.html`.
  - **EXPERIENCE.md Key Flows**: Flow 1 steps 1–3 → `key-home-smart.html`, steps 4–5 → `key-results-thandi.html`, step 6 → `key-hotel-bestfit.html`; Flow 3 step 2 → `key-results-weak.html`.
  - **DESIGN.md Components** inline: Smart search box, Character counter and Submitting → `key-home-smart.html`; Criteria chip, Match reason and Best-fit room line → `key-results-thandi.html`; Notices → `key-results-weak.html`; Best fit chip → `key-hotel-bestfit.html`. DESIGN.md Layout & Spacing (Home, Search results desktop and phone) → the same Home and results mocks.
- **medium** The memlog records "Mock coverage: add fallback-notice alternate (user)", but none of the four mocks has a fallback alternate (`.memlog.md`; `.working/key-*.html` ALTERNATE panels cover Submitting, Reason loading and the unknown-place notice only). *Fix:* add a Fallback alternate (notice, MVP order, no reasons, Query kept in the box) to `key-results-thandi.html` before promotion, or record in the memlog that it was dropped.
- **low** Unchanged MVP surfaces that Smart search reuses, such as the no-results state with city tiles and the three skeleton cards, could point to the MVP mocks. *Fix:* optional one-liner in EXPERIENCE.md Foundation: "Surfaces not mocked here look as in `../../initiative-checkinn-mvp/ux-checkinn/mockups/`."

## 6. Bloat & overspecification — strong
Lean for a delta. Pixel values appear only where no root token exists (56px box height, 2px and 1px border widths, the 20px spinner), and each is justified. No persona or FR restatement. Tables carry the behaviour. Inspiration earns its place, because it records the rejects the user decided.
### Findings
- **low** The weak-match rule ("a heading, not a notice") is stated in five places: DESIGN.md Notices, EXPERIENCE.md Notice row, the Weak match state, Accessibility Floor and Flow 3. The hero-gradient drift in §7 shows how restated rules diverge. *Fix:* keep the normative rule in the Weak match state and have the other places refer to it.
- **low** DESIGN.md Typography repeats the type role of each component, which the YAML and Components already carry. *Fix:* optional. Trim it to the two rules not stated elsewhere: `input-mobile` prevents zoom on focus, and the breakdown is not monospace.

## 7. Inheritance discipline — adequate
`sources` resolve in both files: `../../../DESIGN.md` reaches the repo root, and `../../initiative-checkinn-mvp/...` reaches the MVP spine. UJ titles are verbatim. The guest-facing Glossary terms (Smart search box, Query, Criteria chip, Preferences, Strong match, Ranking blend, Best-fit room, Match reason, Provider) are used as defined, and the token references resolve by name.
### Findings
- **high** The spines contradict each other on the Home hero gradient. DESIGN.md Colors says the shipped hero ("Find your stay." in Brand Blue, `src/app/page.tsx`, which is confirmed to have no gradient) has no gradient line, so the box border is Home's one gradient. The memlog agrees ("hero gradient token dropped (shipped hero has none)"). But EXPERIENCE.md IA (Home row) says "The hero headline loses its gradient while the box is shown". The Provider not configured state says "Home keeps its gradient headline". DESIGN.md Do's says "the hero headline goes plain". A builder following EXPERIENCE.md could add a gradient to the hero for the no-Provider case. *Fix:* in EXPERIENCE.md IA and the Provider not configured state, say "the hero stays as shipped (Brand Blue, no gradient)". Reword the DESIGN.md Do's line to "the box border is Home's one gradient; the hero stays plain".
- **medium** Criteria chip removal pushes a new URL but keeps focus in the chip row and announces the count through a live region. The MVP rule is "focus after navigation goes to the headline… live regions are only for updates in place" (MVP EXPERIENCE.md Interaction Primitives and Accessibility Floor). The delta does not mark this as a deliberate exception, so a builder may apply the MVP rule (EXPERIENCE.md Component Patterns, Criteria chip; Interaction Primitives, Focus). *Fix:* add "Exception to the MVP focus-after-navigation rule: chip removal is treated as an in-place update" to Interaction Primitives.
- **low** "Smart ranking" (EXPERIENCE.md Component Patterns, Search bar (changed)) is not a Glossary term, though the PRD uses it in FR-2 and FR-5. "Best fit chip" drops the hyphen that the Glossary's "Best-fit room" carries. *Fix:* use "Ranking blend order" instead of "Smart ranking", and pick one spelling, "Best-fit chip".
- **low** PRD SM-6 still says "weak-match notice", while FR-10 and both spines say the heading carries it. The spines are right. *Fix:* flag this back to the PRD so the eval metric checks the heading.

## 8. Shape fit — adequate
DESIGN.md sections are in canonical order (Brand & Style → Colors → Typography → Layout & Spacing → Shapes → Components → Do's and Don'ts). Elevation is omitted, which is defensible because nothing changes. EXPERIENCE.md has every required default, plus Responsive & Platform (multi-surface) and Inspiration & Anti-patterns (the memlog records rejects).
### Findings
- **medium** State Patterns is a one-line stub ("Smart search adds the states in **Smart search states** below"), and the table sits under an invented sibling H2, "Smart search states" (EXPERIENCE.md lines 83–106). A consumer extracting by the canonical section name gets nothing. *Fix:* put the table directly under `## State Patterns` (keep the one-line MVP-inherits sentence) and drop the extra H2, or demote it to `### Smart search states`.
