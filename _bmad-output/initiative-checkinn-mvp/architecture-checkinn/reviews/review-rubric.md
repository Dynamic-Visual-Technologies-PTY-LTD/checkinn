# Rubric Review — Architecture Spine: CheckInn MVP

- **Spine:** `architecture-checkinn.md` (status: draft, altitude: feature, 14 ADs)
- **Reviewed against:** spine template, PRD `prd-checkinn.md` (FR-1 to FR-27, §5, §7.2), addendum, memlog, brownfield repo (`package.json`, `next.config.ts`, `playwright.config.ts`, `vitest.config.mts`, `.gitignore`, `.github/workflows/ci.yml`, `AGENTS.md`), Next.js 16.4 bundled docs
- **Date:** 2026-10-09

## Verdict: adequate

This is a strong spine. The paradigm is clear, the ADs are concrete and testable, the conventions table is the right size, and the capability map covers FR-1 to FR-27. It also handles the Next 16 `cacheComponents` trap, which most spines miss. It ratifies the brownfield shell: it keeps `next.config.ts` unchanged by using a plain `<img>` instead of `next/image` remotePatterns and relying on `serverExternalPackages`, uses the `@/` alias, and leaves CI untouched. Stack versions check out against npm today (better-sqlite3 13.0.3, drizzle-orm 0.45.4, drizzle-kit 0.31.11, @types/better-sqlite3 9.6.0, tsx 4.23.15). The mermaid is valid and no template comments remain.

It stops short of "strong" because two ADs contradict each other on the most important write path (AD-2/AD-4 against AD-3). It also leaves three real divergence points undecided: how the confirmation page is gated, the request-time rule for clock and UUID, and test-DB isolation. Finally, the operational envelope at the expo has holes that bear directly on SM-2: reset against a live server, an insecure context on phones, and recovery after a crash.

## Findings

- **[critical]** AD-3 and AD-2/AD-4 contradict each other on the booking transaction (AD-3, AD-4, AD-2, booking sequence diagram). AD-3 needs one *synchronous* `db.transaction(...)` that re-computes Availability. AD-4 says the single `getAvailability` query in `features/hotels/queries.ts` feeds everything, and the sequence diagram calls `getAvailability` inside the transaction. AD-2 says every exported function in `queries.ts` must `await connection()`, so `getAvailability` is async. better-sqlite3 transactions cannot span an `await`: the transaction commits at the first await, the re-check runs outside it, and overselling becomes possible (PRD §5, FR-22). Builders will go two ways here. One calls the async query and silently breaks atomicity. The other copies the SQL into the action and breaks AD-4's "one query". *Fix:* split the query in two. A synchronous, non-exported core `availabilityFor(db, hotelId, stay)` lives in a server-only module such as `src/features/hotels/availability.ts` and takes no `connection()`. `getAvailability` wraps it as `await connection(); return availabilityFor(...)`. Inside `db.transaction`, the booking action calls only the sync core. Update the AD-4 rule, the AD-2 scope ("exported page-facing reads"), and the sequence diagram to match.

- **[high]** AD-2 covers database reads only. It does not cover the clock or random values, but Cache Components treats `Date.now()`/`new Date()` and `crypto.randomUUID()` as values that must be deferred to request time (`node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`, "Random values and timestamps") (AD-2, AD-8, AD-9, AD-10). Several places are exposed. The criteria defaults ("tomorrow", AD-8) on any page that doesn't await `searchParams` could be computed at prerender, which freezes "tomorrow" at build time or breaks the build. The same applies to Home (FR-27/FR-1 defaults) and to the `idempotencyKey` UUID "included in each booking form render" (AD-10). It is also unclear whether the key is generated on the server or in the browser: the memlog says "client-generated" and the spine says "form render". *Fix:* broaden AD-2 to "anything that reads the database, `clock.ts`, or generates a random id runs at request time: after `await connection()` or awaited `searchParams`, inside `<Suspense>`". Have AD-10 state where the key is generated. A server-side `crypto.randomUUID()` after `connection()` is recommended, given the insecure-context finding below.

- **[high]** The confirmation and Booking view gating is undecided (Conventions "Routes", AD-3, AD-10). After a successful confirm, the action redirects to `/bookings/CI-XXXXXX`, but that route is "gated by email" and AD-10 requires both the reference and the email. The spine never says how the email reaches the confirmation page straight after booking. Without that, one builder will put `?email=` in the URL, which leaks PII into history and logs and conflicts with the logging rule. Another will set a cookie. A third will show the page without a gate. *Fix:* add an AD. For example: after confirm or a successful manage lookup, set a short-lived httpOnly cookie listing the references this browser may view, and have `/bookings/[reference]` render when the cookie grants it, otherwise ask for the email. State that email never appears in a URL.

- **[high]** `npm run db:reset` deletes the database file while the expo server may still be running (AD-6, AD-12, FR-26). The presenter laptop holds one open WAL connection. On Windows, unlinking an open file fails (EBUSY). On POSIX, the live process keeps writing to the deleted inode, so the reset looks successful but the app still shows the old Bookings. Either way, "reset between sessions" without a restart (SM-2) is undefined. *Fix:* state in AD-6/AD-12 that reset runs inside one transaction (`DELETE FROM booking_lines; DELETE FROM bookings;` plus a catalog re-seed) on the same file and never deletes it. Alternatively, say "reset requires the server stopped" and add a stop → reset → start step to the operating envelope. Fresh-clone parity still holds because the migrate-and-seed path is unchanged.

- **[high]** The expo network envelope is not a secure context, and the spine is silent on what that breaks (deployment diagram, AD-13, FR-9, FR-22 copy reference). Phones reach `http://<laptop-ip>:3000`. `navigator.clipboard.writeText` (Share in FR-9, copy reference) and `crypto.randomUUID()` in the browser are only available in secure contexts, so they will fail on visitors' phones while working on `localhost` during development and CI. *Fix:* add a rule to AD-13 or a new operations AD. Either serve HTTPS on the stand (a local certificate, an ask-first item), or require a non-secure-context fallback (`document.execCommand("copy")` or a selectable text field with a "copy failed" toast) and generate ids on the server. Cover it with a Playwright check against a non-localhost origin, or list it explicitly as an expo dry-run check.

- **[medium]** The operational envelope is only partly decided (Deferred, deployment diagram). The expo topology is decided: one Node process, `next start -H 0.0.0.0`, phones on Wi-Fi. Several things are not: the environments list (dev, CI/e2e, expo) and which DB path each uses; that the expo must run a production build and never `next dev` (Next 16 `allowedDevOrigins` blocks LAN dev resources); the firewall and port the laptop must open and how visitors get the URL; and what happens on a crash under the "no restart" target in SM-2 (supervisor or manual restart; the DB file survives because of WAL). Backup of the expo DB is also unaddressed. *Fix:* add a small "Environments & operations" table to the Structural Seed covering environment, command, `CHECKINN_DB_PATH`, network exposure, and reset/restart procedure. Name crash recovery as a decision or an open question.

- **[medium]** The test-database strategy is stated but cannot be met with the current harness (Conventions "Tests", Deferred "CI database setup"). `playwright.config.ts` has `fullyParallel: true`, two projects (desktop and Pixel 7), `reuseExistingServer` locally, and no `CHECKINN_DB_PATH` in `webServer.env`. Locally, e2e therefore reuses the developer's `data/checkinn.db` rather than "a fresh database per run". In CI, parallel booking tests across both projects share one database and will race on "Only N left", "Sold out", and cancel flows. The claim that "e2e uses a temporary `CHECKINN_DB_PATH`" is a decision filed under Deferred. *Fix:* move it to a rule. `webServer.env.CHECKINN_DB_PATH` points at a temp file, reset before the run, and e2e specs that mutate Bookings use dates or hotels unique per test or project (or run serially). Editing `playwright.config.ts` is not ask-first.

- **[medium]** Vitest cannot import `server-only` modules as specified (AD-1, Conventions "Tests"). AD-1 requires `import "server-only"` at the top of every `src/db` file and every `queries.ts`/`actions.ts`, and the test convention says queries and actions are tested in Vitest against `:memory:`. `server-only` is not in `package.json` or `node_modules`; Next aliases it internally, which the Next docs say makes installing it optional, but Vitest does not. Even once installed, its default export throws outside the `react-server` condition, and `vitest.config.mts` runs under jsdom. *Fix:* the spine should state the mechanism. One option is a Vitest alias that maps `server-only` to an empty module, set in `vitest.config.mts` with `environment: "node"` for `src/features/**` and `src/db/**` tests. The other is to install `server-only` (ask-first) and add it to the Stack table.

- **[medium]** The Booking snapshot fields are undecided (ERD, AD-3, AD-9, PRD Glossary "Booking"). The PRD says a Booking holds "the Hotel's Cancellation policy at the time of booking" and a Booking total. The spine's cancel path "re-checks the Cancellation policy and deadline" without saying whether it reads from the Booking or the Hotel. It also doesn't say whether `booking_lines` stores the nightly price. Builders of confirmation, manage and cancel will diverge. *Fix:* add one line to AD-3 or AD-9. `bookings` stores `cancellation_policy`, `cancellation_deadline` (ISO UTC) and `booking_total_rand`; `booking_lines` stores `nightly_price_rand`; display and cancel read only these snapshots.

- **[medium]** The dependency diagram is missing edges the ADs rely on (Design Paradigm diagram, AD-1, AD-8). AD-8 has pages parse criteria with `src/domain/criteria.ts`, but there is no `app → domain` edge. AD-1 says "follow the diagram", so this reads as forbidden. `src/lib` has no outgoing rule, and whether `lib` may import `domain` is unstated. *Fix:* add `app --> domain` with the label "codec and types". State that `src/lib` imports nothing from `src/*` (or only `domain`).

- **[low]** Email matching is not normalised (AD-10). Reference lookup is normalised, but email is not. Storage and comparison may differ in case and whitespace, which leads to false "Booking not found" results (FR-23). *Fix:* "emails are stored and compared trimmed and lower-cased."

- **[low]** AD-11 and AD-3 disagree on the success return (AD-3, AD-11). AD-11 says every action returns `{ ok: true, … }`, while AD-3 says success calls `redirect()`, which throws. *Fix:* "on success, booking actions `redirect()` and do not return; the union's `ok: true` branch applies to actions that stay on the page".

- **[low]** Leftover assumption tags and seed tidiness (Stack). `drizzle-orm`, `drizzle-kit` and `tsx` still carry `[ASSUMPTION]`, although Drizzle is in the AGENTS.md agreed stack and the versions are verified. The native build of `better-sqlite3` on Windows workshop laptops (SM-3, fresh clone) is a risk the spine doesn't mention. *Fix:* drop the tags or list the install as a pending ask-first approval in an Open Questions line. Note "prebuilt binary for Node 24 required; verify at the dry-run".
